# Open FastFlowLM XCLBIN and Kernel replacement plan

## Decisions and Assumptions
- For the open embedding integration into upstream FastFlowLM, should we keep the closed `libgemma_embedding.so` as a compile-time fallback (behind `FLM_USE_OPEN_EMBEDDING=OFF`), or should the open engine become the sole embedding path?
  Replace entirely

- Should the Python utility tools (flm-add, flm-test, q4nx-build) and the `flm_model.py` CLI wrapper also be integrated into the upstream CMakeLists.txt as part of this plan?
  Include flm-test only

- For the long-term vision of replacing all model engines, which model family should be the next priority after embedding? This affects how we design the extensibility of the open engine pattern.
  Same architecture family (google/gemma-3-1b-it)

- Where should the `open_embedding` source code live in the upstream repo?
  Inside src/ (Recommended)

## Design Plan: Open Embedding Integration into Upstream FastFlowLM

### Context
FastFlowLM currently ships with a closed-source libgemma_embedding.so for the Embedding-Gemma-300M model. In FastFlowLM_v1.0.1-add, we developed and validated a fully open replacement (open_embedding::Engine) that:
- Loads FP32 weights directly from safetensors via a manifest (no Q4NX)
- Runs the full transformer forward pass in C++ on CPU
- Optionally offloads 5 large matmul projections to NPU2 via bf16 kernels
- Passes the full E-suite (E1-E8) with cosine 0.999993 (threshold 0.999)

The goal is to cleanly integrate this into the upstream FastFlowLM repo, replacing the closed embedding entirely, and establish a pattern for replacing all model engines with open implementations.

- Add (new adapter class):

#### 1.2 Class Hierarchy Simplification
Before (upstream):
embedding_model (ABC, pure virtual, Q4NX-based)
  └── gemma_embedding (closed, pImpl, inside .so)

AutoEmbeddingModel (ABC, has Q4NX, tokenizer, npu_xclbin_manager)
  └── Gemma_Embedding (delegates to gemma_embedding)

After (target):
open_embedding::Engine (standalone, loads safetensors directly)
  - load(model_dir) -> bool
  - embed(text, task) -> vector<float>
  - embed_with_prefix(text, prefix) -> vector<float>

AutoEmbeddingModel (simplified, no Q4NX needed)
  └── OpenGemma_Embedding (owns an Engine, delegates load/embed)
Key simplification: AutoEmbeddingModel::_shared_load_model() currently creates Q4NX, tokenizer, and npu_xclbin_manager. With the open engine, loading is a single engine_.load(model_path) call. The tokenizer is internal to the Engine (via tokenizers_cpp).

#### 1.4 Model Directory Structure
The open embedding expects this layout per model:
```
models/Embedding-Gemma-300M-NPU2/
  config.json
  weights_manifest.json      <- generated by make_manifest.py
  model.safetensors           <- HF safetensors body
  weights/
    2_Dense.safetensors       <- contrastive head 768->3072
    3_Dense.safetensors       <- contrastive head 3072->768
  tokenizer.json
  tokenizer_config.json
  npu_matmul_f32/             <- compiled NPU kernels (optional)
    m512_768x768.xclbin
    m512_768x768.insts
    m2048_768x768.xclbin
    m2048_768x768.insts
    ... (12 xclbin + 12 insts files)
```

#### 1.5 model_list.json Changes
The embedding entry currently has:
`"files": ["config.json", "model.q4nx", "tokenizer.json", "tokenizer_config.json"]`
Needs update to:
"files": ```["config.json", "model.safetensors", "weights_manifest.json", 
          "tokenizer.json", "tokenizer_config.json",
          "weights/2_Dense.safetensors", "weights/3_Dense.safetensors"]```

#### 1.6 NPU Matmul Artifact Management
The 24 NPU matmul artifacts (6 shapes x 2 pads x 2 files) need a home:
- Option A: Bundle into the model directory under npu_matmul_f32/ (current pattern)
- Option B: Shared location under xclbins/ alongside the closed xclbins

Recommendation: Option A — keep them in the model directory. This is self-contained and matches how flm-add installs embedding models. The closed xclbins/Embedding-Gemma-300M-NPU2/ directory (containing attn_full_mask.xclbin, mm.xclbin, mv.xclbin, sliding_attn.xclbin) becomes dead code and can be removed.

#### 1.7 Validation Strategy
1. Build the modified upstream with open embedding only
2. Run full E-suite (E1-E8) against the live server
3. Verify no regressions in LLM, VLM, ASR, or tool-calling suites
4. Test with FLM_NPU_DISABLE=1 to verify CPU-only fallback
5. Test on HRX backend to verify FLM_USE_OPEN_EMBEDDING_NPU is correctly gated

### Phase 2: Gemma3-Text Open Engine (Next Model)

#### 2.1 Architecture Analysis
Gemma3-text shares the same transformer block pattern as Gemma3-embedding:
- Same RMSNorm, RoPE, GQA attention, GELU-MLP primitives
- Same weight naming convention (layers.X.self_attn.q_proj.weight, etc.)
- Same config.json schema

Key differences from embedding:
- Causal masking (causal_lm interface, not embedding_model)
- KV cache management
- Prefill/forward split (batched prefill, single-token decode)
- LM head (vocab projection, not contrastive head)
- Q4NX weights (the open engine would load safetensors directly, bypassing Q4NX)


#### 2.2 Open Engine Pattern for LLM Models
Following the embedding pattern, each new open model engine should:
1. Load weights from safetensors via weights_manifest.json (no Q4NX dependency)
2. Run transformer forward pass in FP32 on CPU (same primitives: RMSNorm, RoPE, GQA, GELU-MLP)
3. Optionally offload matmuls to NPU2 via bf16 kernels (same NpuMatmul dispatch)
4. Implement the causal_lm interface (forward(), prefill(), set_context_length(), etc.)

#### 2.3 Gemma3-Text GEMM Inventory
From the upstream model, the Gemma3-text (1B and 4B) has these matmul shapes:
Shape (K x N)	Weight
768 x 768	q_proj, o_proj (1B)
768 x 3072	gate_proj, up_proj (1B)
3072 x 768	down_proj (1B)
2048 x 2048	q_proj, o_proj (4B)
2048 x 8192	gate_proj, up_proj (4B)
8192 x 2048	down_proj (4B)
768 x 128256	lm_head (1B)
2048 x 128256	lm_head (4B)

This would require new xclbin compilations for the 4B shapes (2048x2048, 2048x8192, 8192x2048).

### Phase 3: Full Open Replacement Pipeline

#### 3.1 Model Family Priority Order
Based on architecture similarity to Gemma3 (same transformer block):

Priority	Model Family	Architectural Similarity
1	Gemma3-text (1B, 4B)	Same as embedding (RMSNorm, RoPE, GQA, GELU)
2	Nanbeige (3B)	Standard transformer (llama-like)
3	Phi4 (4B)	Standard transformer + long/short RoPE
4	Llama3 (1B, 3B, 8B)	Standard MHA transformer
5	Qwen3 (0.6B-8B)	MHA + Q/K norm
6	LFM2 (1.2B, 2.6B)	SSM hybrid (shortconv + delta net)
7	Qwen3.5 (0.8B-9B)	Linear attention + SSM + conv1d
8	Qwen3.6-MoE (35B)	MoE routing + expert dispatch
9	GPT-OSS (20B)	Attention sinks + expert FFN
10	VLMs (Qwen3-VL, Gemma4)	Vision encoder + cross-attention
11	Whisper (ASR)	Encoder-decoder, completely different

#### 3.2 Open Engine Directory Structure
Following the embedding pattern, each new model gets:
```src/open_<model_family>/
  engine.hpp
  engine.cpp
  npu_matmul.cpp```       (shared NpuMatmul class, can be reused)

Or, since the NPU matmul dispatch is identical across models, factor it out:
```
src/open_embedding/engine.cpp          (embedding-specific forward)
src/open_gemma3/engine.cpp             (causal lm forward)
src/open_common/npu_matmul.cpp         (shared NPU dispatch)
```

#### 3.3 Build System Evolution
The CMakeLists.txt should evolve to support multiple open engines:
```
option(FLM_USE_OPEN_EMBEDDING "Replace closed embedding with open engine" ON)
option(FLM_USE_OPEN_GEMMA3 "Replace closed gemma with open engine" OFF)
#Future: option(FLM_USE_OPEN_LLAMA3 ...)*
#Future: option(FLM_USE_OPEN_QWEN3 ...)*

if(FLM_USE_OPEN_EMBEDDING)
    list(APPEND SOURCES src/open_embedding/engine.cpp)
    target_compile_definitions(flm PUBLIC FLM_USE_OPEN_EMBEDDING=1)
endif()
if(FLM_USE_OPEN_GEMMA3)
    list(APPEND SOURCES src/open_gemma3/engine.cpp)
    target_compile_definitions(flm PUBLIC FLM_USE_OPEN_GEMMA3=1)
endif()
```
Each lib*_npu.so would be conditionally excluded from linking when its open replacement is enabled.

#### 3.4 Validation Per Model
Each new open engine must pass:
1. E-suite (adapted per model type): E8 reference agreement for embedding, perplexity/cosine checks for LLM
2. NPU offload validation: E8-style cosine check between NPU and CPU paths
3. Performance benchmarking: Tokens/sec comparison with closed engine
4. Cross-backend testing: XRT and HRX


### Phase 4: Python Tooling (Minimal)

if(NOT WIN32)

#### 4.2 Test Infrastructure
The E-suite for embedding models is already complete. For LLM models, the existing --llm suite provides basic validation. No new test infrastructure needed for Phase 1-2.

##### Risks and Mitigations
Risk	Impact
Breaking closed LLM models when modifying CMakeLists.txt	High
Tokenizers-cpp dependency conflicts	Medium
HRX backend incompatibility with NPU matmul	Medium
Weight format differences (safetensors vs Q4NX)	Low for embedding, High for LLMs
Model download size increase (FP32 safetensors > Q4NX)	Low
