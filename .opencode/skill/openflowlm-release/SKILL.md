# OpenFlowLM release

A release is a tag. `.github/workflows/release.yml` builds five artifacts from
it and publishes them as one GitHub release. The process is in
[RELEASE.md](../../../../RELEASE.md); this skill is the part that is easy to get
wrong, and the traps below are all real ones that cost a cycle.

```
verify ──┬── linux (deb rpm tgz) ── nix ──┐
         └── windows (msi, if staged) ────┴── publish
```

## The only two things CI cannot build

| Input | Built by | Why not CI |
| --- | --- | --- |
| `src/xclbins/*/open_kernels*`, `src/xclbins/BERT-h*` | `utilities/release/stage-prebuilts.sh` on an NPU machine | The open kernel sets compile without a device, but the BERT design sets allocate NPU tensors, so `export-kernels.py --force` needs pyxrt and a card. |
| `xrt_coreutil.lib` + XRT headers | `utilities/release/stage-prebuilts-win.ps1` on a Windows machine with the Ryzen AI driver | The NPU *driver* is the runtime. The import library is made from the driver's `xrt_coreutil.dll`; the headers come from XRT with `xrt/detail/version-slim.h` generated by hand. |

Both are committed to a long-lived `staging` branch (`main` plus the
prebuilts; never merged back). A release is tagged from `staging`, so the
checkout already has the binaries and there is no fetch job. `main` holds
`OFLM_VERSION` and the notes; each cycle is `git merge main` on `staging`,
then the two scripts, then the tag. The tag is not an ancestor of `main`.
That is the point.

`prebuilts/manifest.json` is schema 2, one `platforms.<name>` section per
script. Each script rewrites only its own key, so a lost push race is resolved
by taking origin's file and re-applying that key. `verify-prebuilts.py` is
what the workflow runs, and what to run locally before the tag: it checks
`for_version`, the `open_kernels` / `npu_offload` tree hashes, the file count,
and that a `windows` section has both the headers and the import library.

**The payload layout is `src/xclbins/<family>/open_kernels/<kernel>/`** —
`open_kernels` is a *directory*, and `.gitignore` is
`src/xclbins/*/open_kernels*/` with a trailing slash, so it matches the
directory and not a file called `open_kernels*.xclbin`. That is also the shape
`verify-package.sh`'s `EXPECT_KERNELS` regex assumes
(`xclbins/[^/]+/open_kernels[^/]*/.*\.xclbin$`). Collection is
`git check-ignore --no-index`, not `git ls-files --others --ignored`: after
the first staging commit those files are *tracked*, and `--others` finds
nothing the second time. A file the ignore rules would not ignore is invisible
to the script, which is the one way to ship a package with no kernels.

## Before a tag

- `OFLM_VERSION` in **both** `CMakePresets.json` and `src/CMakePresets.json`.
  `verify` fails the run if either disagrees with the tag.
- `utilities/release/release-notes.md` — published verbatim as the release
  body, so it belongs in the release commit, not after it.
- `VCPKG_REF` in the workflow if a Windows dependency changed. It is a vcpkg
  **date tag with dots** (`2026.07.29`); a dash is not a vcpkg tag, and an
  unpinned `master` means the same tag can produce a different MSI on a re-run.

## Workflow traps (all hit while building this)

- **`cpack -G DEB -G RPM -G TGZ` is last-wins, not a list.** It writes one TGZ,
  exits 0, and looks fine until the missing formats are noticed by hand. Run
  `cpack -G <gen>` once per format; a generator *list* in `CPACK_GENERATOR` (what
  the `linux-package` preset uses) does work.
- **Tag filters are globs, not regexes.** `v[0-9]+.[0-9]+.[0-9]+` matches
  nothing: `+` is literal. The pattern is `v*.*.*`, and the strict `X.Y.Z`
  check is a shell step in `verify`, where the error can explain itself.
- **`env` is not available in `jobs.<job_id>.name`** (that context list is
  `github, needs, strategy, matrix, vars, inputs`). GitHub rejects it and so
  does `act`.
- **`needs.<job>.result` only exists for a job in `needs`.** To attach the MSI
  conditionally, `windows` must be in `needs`, and then the dependent job needs
  `if: !cancelled() && ...` because a *skipped* need skips its dependents. A
  skipped MSI must still publish the rest; a *failed* one must not.
- **`env` cannot reference itself.** Two `OFLM_VERSION:` keys is invalid YAML.
  The version is `${{ inputs.tag || github.ref_name }}` at the top level, which
  works for both triggers.
- **A multi-line PowerShell here-string cannot live in a YAML `run: |` block.**
  Its unindented body ends the block and the file stops parsing. Put the
  explanation in a `.md` and `throw (Get-Content ... -Raw)`.
- **PowerShell + `GITHUB_ENV`**: `"K=V=$x" >> $env:GITHUB_ENV`. Writing to
  `$GITHUB_OUTPUT` does not set an env var for later steps.
- **Unquoted `2025-08-07` is a YAML date.** Quote version-like scalars.
- **Ninja on windows-2022 fails** — no `cl.exe` on PATH outside a developer
  prompt. Use `-G "Visual Studio 17 2022" -A x64`, which is what
  `src/build-windows-vcpkg.cmd` uses and is the only known-good configuration.
- **`VCPKG_ROOT` must be a job-level env var.** `get_files.bat` stages
  `%VCPKG_ROOT%\installed\x64-windows\bin\*.dll` into the MSI; without it the MSI
  installs cleanly and `oflm.exe` then fails to start with a missing DLL.
- **`tokenizers-cpp` is a gitlink in the index**, so `submodules: recursive`
  gets the commit the tag records. Do not clone it in the workflow: that builds
  a different source than the tag. It is also a Rust crate — check `cargo`.
- **`sentencepiece` needs an abseil junction** after the first configure
  (`New-Item -ItemType Junction`), then a second `cmake` pass. Both
  `build-windows-vcpkg.cmd` and the workflow do this.
- **Do not collect staged kernels with `git ls-files --others --ignored`.**
  That lists only untracked files. After the first commit to `staging` the
  kernels are tracked, so the query returns nothing and the script reports
  "no built kernels" with a full tree sitting there. `git check-ignore
  --no-index` answers "would this path be ignored if it were untracked", which
  is the question, for tracked files too.
- **`$name:` in a PowerShell double-quoted string is a drive-qualified
  variable**, not "the variable, then a colon". `"origin/$Branch:prebuilts/..."`
  expands to `origin/`. Write `${Branch}`.
- **A rejected push is a merge, not a rebase.** `--ours` and `--theirs` mean
  opposite things in the two, and a rebase wants an editor. The scripts take
  origin's manifest with `git show origin/staging:prebuilts/manifest.json` and
  re-apply their own section. Do not force-push over the other machine.
- **`gh release view` needs `GH_TOKEN`**, even to *check* for an existing
  release.

## Checking the pipeline before you push a tag

`act -l` validates the workflow without a container (it parses the DAG, the
context references and the job graph):

```bash
act -l            # lists jobs; an invalid context or property is a hard error
```

To exercise the staging chain for real, without an NPU and without touching
`origin`: clone to a scratch dir, `git init --bare` a throwaway origin, create
`staging` from `main`, drop ignored files under `src/xclbins/<family>/
open_kernels/`, then `stage-prebuilts.sh --no-build`. A second clone that
pushes a `windows` section while the first is committing is the race; the
script must merge, keep both sections, and not force-push. Then
`verify-prebuilts.py`. `--no-build` is the flag, or you will spend twenty
minutes compiling kernels.

## MSI specifics (`src/wix/`)

- `PackageDir` is `package`, the directory `get_files.bat` empties and fills. It
  was `$(SourceDir)` (`../inno`, which nothing writes) and briefly `.`, which
  would glob `oflm.wxs`, `build.ps1` and `output/*.msi` into Program Files.
- The payload is `<Files Include="$(PackageDir)\**" />` rather than 45 hand
  listed `<File>`s: a hand-written list is a claim nothing checks, and a missing
  vcpkg DLL shipped an MSI that could not start. `check-wix-payload.ps1` runs
  in CI to catch the reverse (a file staged but not in the MSI).
- `ProductVersion` is `-d ProductVersion=…` from the tag. The old hardcoded
  `1.0.4` meant every release was the same MSI version: it upgrades nothing.
- `terms.rtf` and `logo.ico` are read from `../inno`; `terms.rtf` is
  deliberately **not** staged, or the licence text installs into Program Files.

## Nix specifics

`nix/default.nix` packages the release TGZ with a `fetchurl`/`sha256`, because
XRT is not in nixpkgs and a from-source build would need it vendored as a
fixed-output derivation. The pin (`nix/pin.json`) is data because a flake
cannot take an argument. The release ships its own flake
(`openflowlm-<version>-nix.tar.gz`), so the repository pin can lag by one commit
— a release asset URL is a valid flake ref. The derivation's `checkPhase` runs
`oflm --version` and `oflm list` from the store, which is what catches a store
move that broke the relative `RUNPATH`.

## Checking a release

```bash
# What a package must contain (this is what the workflow runs):
utilities/release/verify-package.sh build/packages --version 1.2.3

# The same check the release workflow runs, before you tag:
utilities/release/verify-prebuilts.py
```

`verify-package.sh` failing on "no open kernel files" against a *local*
`OFLM_BUILD_KERNELS=OFF` build of `main` is correct, not a bug: the kernels
live on `staging`, and a checkout of `main` has none. Check out the tag.

## Fixing a bad release

Fix forward, never re-tag. The RPM and DEB keep the filename and version of a
published release, and a user who already installed it will not get the fix:
`gh release delete v1.2.3 --yes`, fix, tag `v1.2.4`.
