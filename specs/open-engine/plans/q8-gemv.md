# Plan: q8 weight projections on the main cores — stop re-quantising what the author shipped at q8

**Status:** designed 2026-09-06 (Fable), approved by Cyrus, implementation delegated
(code-only, in a worktree while the NPU validates the re-quantised path). Not built.
**Spec impact:** one new requirement `OPEN-QUANT-Q8`; `OPEN-PACK-PLAN` gains the q8 band
law; `OPEN-SPEC-DERIVE` gains the per-role quant map; new catalogue template `gemv_q8`.
**Supersedes, for the affected tensors:** the transparent q8→q4_1 re-quantisation in
`container-formats.md` — which stays as the *fallback* wherever a design cannot afford q8.

## Why

FLM's newer converter stores every non-expert projection of the 35B-A3B fine-tunes
(251 of 733 tensors: attention q/k/v/o/gate, linear qkv/z/out, the shared expert) and the
`ssm_out_proj` + alpha/beta of every Qwen3.5 dense model at **q8**. The open engine today
re-quantises those to q4_1 on the way into the pool. Measured cost on the 9B's out-projection:
0.997 correlation on that projection's output, 0.9997 logits correlation on a 4-layer slice
(`.claude/plans/q-qwen35-handoff.md`, R3). Small per layer, compounding over 32–40 layers,
and it serves the newest models at FLM 1.0.2's quality when the author chose 1.0.3's.
Native q8 removes that gap: the pool holds the q8 values as shipped and the kernel
consumes them.

## What exists

`designs/lm_head_q8/lm_head_q8.h` already does q8 on the matrix unit: `gemv_q8_tile`
takes an 8704-byte chunk (`scales[256] bf16 | codes[8192] int8`, the same 32-row × 256-K
tile as a q4 chunk, rows in order so no lane permutation), the same int16 activation
table (`gemv_tab.h`), and accumulates 32 rows per k-tile. It is DMA-bound like the q4
kernel. What it lacks for the main cores: a runtime K (it reads `LMHEAD_K`), a pool band
law, and a chunk that fits the main cores' weight stream.

## Design

### 1. The q8 pool chunk: a 16-row half-tile in a 5 KB element

The main cores' w-fifo element is `PER_CALL × 5120` bytes (10 KB on the 27B, 5 KB on the
9B). An 8704-byte q8 chunk fits neither cleanly. Split it into two **half-tiles** of
16 rows × 256 K:

    q8h chunk, 5120 B:  scales[128] bf16 at [0 : 256]     index kb*16 + r   (r = 0..15)
                        codes [4096] int8 at [256 : 4352]  index k*16 + r
                        pad            at [4352 : 5120]

From a container q8 chunk (rows 0..31) the host takes half `h`: `scales_h[kb*16 + r] =
scales[kb*32 + 16h + r]`, `codes_h = codes[h*4096 : (h+1)*4096]` verbatim (the container's
row-block stride is exactly 4096 codes, `lm_head_q8.h`). A byte permutation, no arithmetic.
The 768-byte pad is 15 % of the stream on q8 tensors only; the alternative (a 4352-byte
element type) would change every design's fifo element and is not worth it.

**Band law** (`q8_perm`, the q8 twin of `std_perm`): a band is still 64 output rows × K,
now `4 × K/256` half-chunks; half-chunk `c` inside its band: `part = c % 4` (rows
16·part..), `kt = c / 4`. Bytes per band = `2 × band_bytes(K)`, as q8 should be. The
container's raster order for the source is the same as q4's (file chunk `f` covers rows
`32·(f / ncol)`, cols `256·(f % ncol)`), so `q8_perm(c) = (file chunk of rows
64·band + 32·(part/2), k-tile kt, half part % 2)`.

### 2. The kernel: `gemv_q8_half` on the main cores

`designs/gemv_q4/gemv_q8.h` (new; sibling of `gemv_q4.h`, sharing `gemv_tab.h`):

- `gemv_q8_half_tile(tile, tab, K, kt, first, y16)` — `lm_head_q8.h`'s loop over one
  `c0` row block only (rows 0..15: `Clo` = rows 0..7, `Chi` = rows 8..15), 16-lane
  `accfloat` accumulator, `scales + kb*16`, runtime `K` for the table offsets, no `last`
  (rows are in order). `noinline + inline` (COMDAT) like the q4 body.
- `gemv_q8_pool_group_rt(chunks, tab, group, y, per_band)` — the q4 `_rt` wrapper with
  `rs = 4` and 16-row parts: `part = c % 4 → y + 16·part`, `kt = c / 4`, `first = kt == 0`.
- Entry `gemv_q8_gy(e, tab, y, group, per_band, band)` generated by both `gen_kernels.py`
  (layer_x and dense) exactly as `gemv_q4_gy` is, one TU, one symbol.

`gemv_bands` (xcommon) already takes the entry, `per_band` and `rs` as arguments; a q8
projection is `gemv_bands(win, yout, tab, K["gy8"], nbands, 2·ngroups, 2·per_band, 4)`.
The band's y element (64 floats) is unchanged, so the y stream, the drains and every
downstream stage are untouched.

### 3. The recipe knows which tensors are q8: `ModelSpec.quant` becomes a map

`config.json` does not say. The container does, and so does a GGUF. `ModelSpec.quant`
(today the string `"q4_1"`) becomes a per-role map derived at spec time from the
container header (`--model-dir`: read `model.q4nx`'s safetensors header, 8704-byte
chunks ⇒ q8) or the GGUF tensor types:

    quant: {"attn": "q4_1" | "q8", "linear": ..., "linear_out": ..., "shared": ...,
            "ffn": ..., "experts": "q4_1", "lm_head": "q8" | "q4_1"}

with `"q4_1"` everywhere the default (the FastFlowLM 1.0.2 layout; every checked-in spec
and fixture keeps deriving byte-identically). Roles, not tensor names, so the recipes
stay readable; the deriver maps tensor names to roles once. A container whose tensor
format disagrees with the manifest's role map is refused by the packer naming the tensor
(the packer already knows the source chunk size per tensor since `container-formats.md`).

Consequences, all mechanical:

- `layout()`: a q8 role's pool region is `2×` the q4 bytes; the pool grows past 512 MB
  on the 35B variants (linear layers ~541 MB, attention layers ~543 MB by the current
  offsets) — `POOL_BYTES` becomes `max(512 MB, roundup(end, MB))`, keeping the shipped
  27B at 512 MB byte for byte. Resident memory on a q8-variant 35B rises by roughly
  0.8 GB of weights plus the pool rounding; say the number in the result.
- `pack_plan()`: `q8_perm` instead of `std_perm` for a q8 role (the expert ops stay q4_1;
  a q8 routed expert is refused by name — no model ships one). `C_WOUT` (the linear
  out-projection, in consts on the MoE design) follows the same rule.
- `programs()` / the designs: per projection, the entry and band bytes come from the
  role's quant (`Linear.QKV_Q8`, `Attn.Q_Q8`, …, or simply a `q8 = {"qkv", "z", …}` set
  on the recipe). The host sequence's fills double their byte counts for q8 bands; the
  core program calls `gy8` there. `dx.py` gets the same switch for `ffn` / `attn` roles
  (no shipped dense model needs it today, but the code path should not be MoE-only).
- `build_key` / `spec_hash`: the map is part of the spec, so a q8-variant 35B is a
  *different kernel set* from FastFlowLM's 35B (its instruction streams bake in the pool
  offsets and fill sizes). Build dirs get the quant map's short hash in their names.
  "Kernels belong to families": the family is shape + quant map.
- `hf_config_check` cannot check the map; the packer's per-tensor refusal is the check.

### 4. Catalogue

New template `gemv_q8` with `K` (validated set, initially empty → every q8 export needs
`OPEN_KERNELS_UNVALIDATED=1` until the procedure passes), `rows_per_core` multiple of 64,
`per_call` {1, 2}. The `attn` / `deltanet` points are unchanged (the projection's format
does not touch the attention or DeltaNet kernels).

### 5. Replica and tests

`replica.py` / `replica_qwen35.py`: for a q8 role, use the q8 values (the acceptance
reference IS the shipped model now; the `--q8-weights` / `requant` flags collapse — keep
one flag `--requant` that re-quantises for A/B against the old path). Unit tests
(`test_quant_q8.py`): the half-tile split round-trips (`dq(q8h halves) == dq(q8 chunk)`
exactly); the `q8_perm` law against a brute-force placement; NumPy and C++ packers
byte-equal on a synthetic mixed container; the derived quant map for a synthetic header;
every existing fixture derives with an all-`q4_1` map and byte-identical manifests.

## New requirement

### OPEN-QUANT-Q8: q8 projections run at q8
**Applies to:** openflowlm-next (`designs/gemv_q4/gemv_q8.h`, `designs/layer_x/`,
`designs/dense/`, `recipes/{spec,qwen36moe,qwen35,dense,pack,catalogue}.py`,
`src/open_qwen36/{pools,manifest,q4nx_file}.*`, `model/replica*.py`)
**Test category:** manual (needs the NPU and a q8-variant container); the half-tile
split, the band law, the quant-map derivation and the two packers' agreement are unit-tested
in `tests/test_quant_q8.py`

A weight projection the container stores at q8 shall be streamed to the main cores at q8
(16-row half-tiles of the container's chunks, the `q8_perm` band law) and consumed by
`gemv_q8_half`, not re-quantised, whenever the design's core memory allows; the recipe
derives which projections those are from the container (or GGUF) into `ModelSpec.quant`,
the manifest carries it, and the packer refuses a container whose tensor formats disagree
with it, naming the tensor.

**Acceptance criteria (unit):** as §5.

**Procedure (manual):** Ornith-1.0-35B-A3B (q8 attention / linear / shared expert):
export with `OPEN_KERNELS_UNVALIDATED=1`, the 8-layer / 3-token slice against
`replica.py` fed the q8 values — logits corr ≥ 0.99999, same argmax and top-5, residual
corr ≥ 0.9999 every layer (the same bar as the 27B, now against the shipped weights);
the engine CLI bit-identical to the harness; chat; ms/token beside the re-quantised path's
number from `q-hw-results.md`. Then Qwen3.8-Distilled-9B with `linear_out` at q8 (the only
q8 projection in that family): the same, and the logits correlation against the q8
reference must now be ≥ 0.99999 where the re-quantised path scored 0.9997.

## Expected costs, stated up front

- **Bandwidth.** A q8 tensor streams 2× the bytes. On the 35B a linear layer's non-expert
  projections are ~23 MB at q4_1 and ~39 MB at q8 against ~16 MB of routed experts per
  token, so per-layer bytes rise ~40 % and decode drops from ~7 to roughly 5 tok/s. The
  closed engine pays the same on these containers; the honest comparison is against FLM
  1.0.3 on the same file. On Qwen3.5 dense only the out-projection is q8: negligible.
- **Program memory.** One more `noinline` body plus one entry on a core that holds 10–16.
  If the build overflows 16 KB, fold `gemv_q4_gms` into `gemv_q4_gy` first (the q35
  handoff's lever), then `-Oz` on the GEMV TUs. The re-quantised path stays selectable
  per role (`quant` map forced to `q4_1` by an export flag) as the fallback.
- **Memory.** ~+0.8 GB resident on a q8-variant 35B plus the pool BO rounding.

## Order

1. `gemv_q8.h` + the half-tile split + `q8_perm` in NumPy, with the round-trip and law
   tests (pure host, an afternoon).
2. `ModelSpec.quant` map + deriver + fixtures unchanged; `build_key` covers it.
3. Recipes (`qwen36moe`, `qwen35`, `dense`) and the designs' per-role switch; manifest
   fields; both packers; `manifest_test` / `pools_test`.
4. Replica; the `--requant` A/B flag.
5. Spec, README, handoff for the hardware stream (Ornith-1.0 first, then the 9B, then the
   remaining fine-tunes and Atomic-Germ's 35B mirror).

## Not in this plan

q8 routed experts (no model ships them; the expert stripe law would need its own twin),
a q8 activation path (activations stay int16 block-quantised), Q4_K.
